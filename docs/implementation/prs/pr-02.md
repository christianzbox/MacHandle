# PR-02 — Technical Feasibility and Architecture Decisions

## Objective
Resolve the technical boundaries needed before domain and provider implementation.

## Prerequisites
Verify PR-01 merged on GitHub and update from origin/main. Do not treat this
brief's existence as authorization to execute it in the PR-01 session.

## Context
Read [AGENTS](../../../AGENTS.md), [coordination](../pr-coordination.md),
[progress](../progress.md), [architecture](../../architecture/overview.md),
[ADRs](../../architecture/decisions/README.md), [security](../../architecture/security-model.md),

consult only the relevant master-spec sections and current official documentation.

## In Scope
Evaluate Swift/macOS deployment floor; EventKit calendar/reminder permissions and
read/write distinctions; Contacts framework constraints; Google desktop OAuth and
app-created scope; local MCP transport/authentication boundary; sandbox and helper
feasibility; background execution; Developer ID and notarization strategy.
Write focused ADRs with evidence, limitations, and decisions. Use small isolated
synthetic proofs of concept only where needed to answer a specific question.

## Out of Scope
Production providers, complete OAuth, live personal account access, sync, MCP
server, full app UI, release credentials, broad entitlements, and Notes implementation.
PR-26 owns Notes feasibility in depth. Do not connect accounts merely to research.

## Contracts
Maintain three authorization layers. Keep sync and MCP independent. No source writes
from sync. No caller-asserted approval or identity. Default disabled, minimal scopes.
No private APIs or Notes database access. Preserve stable identity decisions for later.

## Security
Identify exact OS vs app policy limitations, code-signing/Keychain identity needs,
helper trust boundaries, and how user content can cross into integrations. Document
what sandboxing actually constrains. Do not broaden permissions speculatively.

## Implementation Notes
For each decision record alternatives, official sources and dates, experiments,
result, and unresolved release blocker. Revisit provisional macOS 14 and bundle ID.
If an experiment needs permission or an external account, describe the exact
synthetic setup first and obtain user involvement; do independent research meanwhile.
External platform uncertainty may produce a defer decision rather than extra scope.

## Tests
Run all existing checks. Add focused synthetic checks for any retained prototype;
remove exploratory code that is not part of the decision artifact. Separate
compilation, mocked behavior, actual OS/API tests, and untested assumptions.

## Acceptance Criteria
ADRs state practical deployment/toolchain baseline, sandbox and process strategy,
OAuth scope/redirect assumptions, MCP trust boundary, background/release approach,
and explicit follow-up blockers. No unverified support is advertised.

## Documentation
Update ADRs, architecture, progress, coordination, roadmap and testing where relevant; refine
PR-03 brief with actual domain constraints. Deliberate product changes require a
clearly documented master-spec update, not a second competing plan.

## Handoff
Open one PR, leave it for review, and stop. List decisions PR-03 can rely on and
unresolved questions owned by later provider/authentication milestones.

## Evidence and experiments

Date: 2026-10-23. Research sources are linked beside their claims in ADRs 0004–0007;
Google method authorization lists were checked individually, including negative
CalendarList/ACL scope cases. Apple documentation was read through its public DocC
JSON when the HTML tool could not render content. No authenticated APIs were used.

Disposable API-availability probes used the repository's strict selected Xcode 27.1
(27A9275), Swift 6.4 and SDK 27.0 at base commit
`4364fb79676de22d07cb6e5c01738481aad1f7d5`; app/package/config remain unchanged.
The positive probe imported EventKit, Contacts, ServiceManagement and XPC, with
function bodies referencing:

- `requestFullAccessToEvents()`, `requestFullAccessToReminders()` and
  `requestWriteOnlyAccessToEvents()` inside an uncalled `@MainActor async throws` function.
- `EKEvent.occurrenceDate`, `calendarItemIdentifier`, `calendarItemExternalIdentifier`,
  `CNContact.identifier`, `CNContactFetchRequest(keysToFetch:)`, `CNContactIdentifierKey`.
- `SMAppService.mainApp` and `xpc_connection_set_peer_code_signing_requirement`, returning
  the latter's `Int32` status from an uncalled function with a synthetic identifier.
  This only checks API availability; production code must check errors and validate
  the intended signing authority as well as identifier.

Each architecture passed this command with the temporary source path substituted:

```sh
# First source Scripts/check_environment.sh and call machandle_check_environment.
# Run separately for arm64 and x86_64; source contains only uncalled functions.
xcrun swiftc -typecheck -swift-version 6 -warnings-as-errors \
  -sdk "$(xcrun --sdk macosx --show-sdk-path)" \
  -target arm64-apple-macosx14.0 Availability.swift
```

The negative probe `import Contacts; let status: CNAuthorizationStatus = .limited`
was rejected at macOS 14 with **'limited' is unavailable in macOS**, matching SDK
availability metadata. That expected compile failure is evidence against assuming
iOS limited Contacts support, not a failing repository check.

Temporary probes were removed; no executable ran and no store was instantiated.
No runtime, mocked provider or security test is claimed. Existing synthetic tests
continue to cover the foundation only. Standard validation is required on staged
PR-02 files and on the final committed snapshot; exact local and hosted evidence
belongs in [coordination](../pr-coordination.md) and the PR description.

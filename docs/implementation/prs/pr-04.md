## Scope and contracts

- Add a cohesive PermissionEngine target depending on CoreDomain only. Model
  connection policies, selected resources, field grants, operation grants, policy
  generations, explicit denial reasons and allowed decisions. No default grants.
- Keep OS authorization, connection enabled/revoked state, authenticated context
  and action approval independent. Client-supplied ConnectionID is a lookup key,
  never evidence of authentication. Establish an explicit trusted caller boundary;
  actual MCP pairing/identity remains PR-19.
- Use typed Calendar/Reminder/Contact operation enums. Creating does not imply
  deleting; reminder completion and due changes are distinct. Inspect every field
  in create/update payloads; generic update permission alone cannot authorize hidden
  fields. `ContactChanges.changedFields` includes explicit clearing.
- Explicit selections must not broaden on empty discovery or unknown identity.
  Match full provider/store/account/resource scope, not display names or bare IDs.
  Supported contact subsets must handle unified/underlying ambiguity by denying
  unresolved scope; do not assume unified views belong to one selected container.
- Field filtering must return only authorized values, preserving not-fetched and
  authorized-empty distinctions. Availability-only output excludes event detail.
  Neither an occupied-time interval nor internal coverage metadata is public by default.
- Revocation and policy changes invalidate subsequent decisions; specify how later
  operations re-evaluate generations at execution and response. No stale allow cache.
  A policy allow is not local approval and cannot execute a ProposedChange.

## Exclusions and security

No Apple permission prompts/providers, OAuth, persistence, sync planner/executor,
MCP transport, trusted approval-token issuance or UI. No real data or entitlements.
Do not add a public serializable approved/authenticated flag. Typed values are not
proof of provider identity, ownership, freshness, or safe mutation preconditions.

## Tests and acceptance

Use synthetic fixtures to verify default deny, disabled/revoked/unknown connections,
OS denied/restricted/write-only reads, namespace collisions, cross-connection policy
isolation, exact resource selection, operation escalation, contact field filtering
and clear-field changes, empty selection, ambiguous contacts and stale generations.
Resource text claiming approval must remain inert. Assert that source sync cannot
receive original-calendar write grants. Keep tests behavioral, not getter coverage.

Run all three standard checks on staged files and record exact local/hosted evidence
separately. Acceptance requires deterministic decisions and filtering without
providers/UI/transport dependencies; it does not establish live authentication.
